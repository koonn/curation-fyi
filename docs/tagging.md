# タグ付けの運用

記事のタグは3段階で決まる。表示用タグは `union(tags, llm_tags)`。

| 段階 | 書き込む先 | 実行者 | いつ走るか |
|---|---|---|---|
| ① ルールベース | `tags` | `pnpm collect` / `pnpm retag` | 毎回（決定的・冪等） |
| ② LLM（APIキーあり） | `llm_tags` + `llm_tagged_at` | `pnpm collect` | `GEMINI_API_KEY` があるときだけ、25件×最大20リクエスト |
| ③ 手動（APIキーなし） | `llm_tags` | `pnpm tag-export` → 編集 → `pnpm tag-import` | 人が回したいとき |

②と③は**同じフィールドに書く同じ仕事**で、どちらか一方があればよい。
`GEMINI_API_KEY` を持たない運用では③が正規の手順になる（現在CIには設定済みで②が動いている）。

②だけが `llm_tagged_at`（判定済みの印）を書く。③は「どのタグにも合わない」と
「まだ判定していない」を作業ファイル上で区別できないため、印を付けない。

## ① ルールベース

`taxonomy/tags.yaml` のキーワードで `title + " " + summary` を判定する。
en キーワードは単語境界マッチ（大文字小文字無視）、ja キーワードは部分文字列マッチ。
`source.type === "paper"` の記事には無条件で `paper` を、`source.default_tags` は union する。

```sh
pnpm retag   # 全記事の tags を再計算して上書きする（llm_tags は触らない）
```

決定的なので、2回続けて実行すれば2回目の `git diff data/` は空になる。

## ② LLM（APIキーがある場合）

`pnpm collect` のタグ付け段階に組み込まれている。対象は
「`tags` も `llm_tags` も空、かつ `llm_tagged_at` が無い」記事から social を除いたもので、新しい順。
**25件を1リクエストにまとめて** `gemini-3.5-flash-lite`（無料枠）に投げる。
`GEMINI_API_KEY` が未設定なら `LLMタグ付け: APIキー未設定のためスキップ` を出して何もしない。

CI では repo の GitHub Secrets の `GEMINI_API_KEY` を使う（設定済み）。

### 無料枠の制約（2026-08-21 実測）

- **15 RPM**（`GenerateRequestsPerMinutePerProjectPerModel-FreeTier`）。**ここが律速**
- `retryDelay` は約20秒。待って再開すれば済む種類の制限
- 1実行の予算は `MAX_REQUESTS_PER_RUN = 20`。cron は1日4回

上限に当たると**その実行を打ち切って正常終了**し、未処理分は次回に回る。
どの制限に当たったかは `QuotaExceededError.detail` としてログに出るので、
「打ち切られた」だけで終わらず理由まで読める（`packages/pipeline/src/llm/gemini.ts`）。

**429で待って再開する処理はまだ入っていない**（積み残しが15リクエスト未満に収まっている間は当たらない）。
Issue #2 の和訳バックフィル（1,578件＝64リクエスト）が乗ると確実に当たるので、そこまでには要対応。

## ③ 手動（APIキーがない場合の正規手順）

**1. 未タグ記事を書き出す**

```sh
pnpm tag-export --limit 100     # 既定100件。data/tagging/pending.jsonl に出る（git管理外）
```

出力は1行1記事の JSONL。`tags` が空で出てくる。

```json
{"url":"...","title":"...","summary":"...","source_id":"...","language":"ja","tags":[]}
```

対象は②と同じ「`tags` も `llm_tags` も空、かつ `llm_tagged_at` が無い記事」から social を除いたもので、並びは新しい順
（サイトのトップに出る記事から埋まるようにしている。social を外す理由は下記）。
要約は読みやすさのため300字で切る。

**2. `tags` を埋める**

`taxonomy/tags.yaml` の slug を0〜3個。**どのタグにも合わなければ空のままにする**。
人がやってもよいし、Claude Code のセッションにこのファイルを読ませて埋めさせてもよい。
利用可能な slug は `tag-export` が実行時に一覧を出す。

**3. 取り込む**

```sh
pnpm tag-import
```

- taxonomy にない slug が1つでもあれば**何も書き込まずにエラーで止まる**（typo を握り潰さない）
- 取り込んだタグは taxonomy 記載順に正規化されて `llm_tags` に入る
- **`tags` が空の行は「未判定」として扱われ、何も書き込まれない**。
  「どのタグにも合わない」と「まだ見ていない」を区別する手段がないため、
  空のまま取り込むと次回の `tag-export` にまた出てくる（下記の既知の課題）

### ソースを絞る

```sh
pnpm tag-export --source vercel-blog --limit 12 --file data/tagging/vercel-blog.jsonl
pnpm tag-import --file data/tagging/vercel-blog.jsonl
```

`--source` はカンマ区切りで複数指定できる。`--file` の相対パスはリポジトリルート基準。

## 空判定の記事が毎回出てくる問題（2026-08-22 解決済み）

②③とも対象条件が「`tags` も `llm_tags` も空」だったので、
**「どのタグにも合わない」と判定された記事が次回も対象に戻っていた**。
対処は下記「### 処理済みフラグを入れた」を参照。以下は判断の経緯の記録。

2026-08-16 に手動で **136件**（新着100件＋未タグ上位3ソースからの層化抽出36件）を判定した実測:

| ソース | 空 | 計 | 空判定率 | 空の中身 |
|---|---:|---:|---:|---|
| discord-engineering | 10 | 12 | 83% | Changelog / Patch Notes / 提携告知 |
| hn-frontpage | 42 | 64 | 66% | 心臓病・エルニーニョ・スポーツ等の一般ニュース |
| vercel-blog | 8 | 13 | 62% | `/changelog/` の製品告知 |
| hatena-hotentry-it | 18 | 32 | 56% | 家電レビュー・政治・防災アプリ等 |
| simonwillison | 1 | 2 | 50% | 野鳥の観察記録 |
| jxck | 0 | 12 | **0%** | — |
| **合計** | **79** | **136** | **58%** | |

空判定は2種類に分かれ、対処も別になる。

**(a) そもそも技術記事でない**（hn-frontpage・hatena-hotentry-it）
この2つは技術限定ではない集約サイトなので構造的に混ざる。

**(b) 技術ドメインだが製品告知**（vercel-blog の `/changelog/`、discord-engineering の Changelog / Patch Notes）
製品告知は本サイトの対象外とする方針。**タグ付けではなく収集/表示の段階で切るべきもの**で、
現に vercel-blog の `/changelog/` 881件のうち **529件は既にルールベースでタグが付いており**、
タグ付け段階だけを直しても表示からは消えない。

見分けの手掛かり（少数標本なので確定ではない）:
- vercel-blog は URL で分かれる。未タグの `/changelog/` 8件は全て製品告知、`/blog/` 4件は全て技術記事だった。
  ただしコーパス全体の未タグ率は `/changelog/` 40% / `/blog/` 41% とほぼ同じで、
  「ルールが両方に同じくらい効いている」だけかもしれない
- discord-engineering はタイトルの `Changelog` / `Patch Notes` で23件（全102件の23%）が機械的に分かれる。
  そもそもこのソースは engineering ブログではなく Discord の一般ブログで、技術記事は稀

### (b) は解決済み（2026-08-16）

製品告知はキュレーション対象外とする方針が決まり、収集段階で除外するようにした。
`data/sources.yaml` の `exclude` と `pnpm prune-excluded` で、904件を削除済み。
詳細は `docs/sources.md`。

### 対象から social を外した（2026-08-16）

`/social/`（HN・はてブ）は技術タグが付かなくて当然の記事が半数を占め、日付順に読むページで
タグを必要としない。そのため**タグ付けの候補から social を除外**した。

- `collect` の LLM 候補と `tag-export` の既定の対象、どちらからも外れる
- `tag-export --source hn-frontpage` のようにソースを明示したときは従来どおり出せる
- 分類の定義は `@curation-fyi/shared` の `CATEGORIES`（site のページ分割と同じものを使う）

実測（2026-08-16）: 未タグ 1251件 → 候補 801件（social 450件が対象外）。

### (a) の残り

カテゴリ別のタグ付与率（2026-08-16 実測）:

| カテゴリ | 付与率 | 未タグ |
|---|---:|---:|
| papers | 100%（`paper` タグが無条件で付く） | 0 |
| tech | 60.2% | 813 |
| social | 39.0%（対象外にした） | 441 |

**tech の未タグ813件は「タグの付けようがない」のではなく「キーワードルールが取りこぼした」ものが主体**。
未タグの55%を占める vercel-blog(240) と jxck(204) は、層化抽出で jxck 12/12・vercel `/blog/` 4/4 が
タグ付け可能だった（jxck は要約が無くタイトルだけなのでキーワードに当たりにくい）。

空判定が残るのは特定のソースに集中する。新着順に取った20件の標本では8件が空判定だったが、
うち6件は simonwillison のリンクブログ（「Northern Gannet」「Quoting OpenClaw」等の短文）で、
**この標本は代表的ではない**（simonwillison は標本の60%を占めるが母集団では3.3%）。

### 処理済みフラグを入れた（2026-08-22）

`Article.llm_tagged_at`（ISO時刻・任意）を追加し、**LLMが判定したら結果が空でも時刻を刻む**。
②③の対象条件を「`tags` も `llm_tags` も空 **かつ `llm_tagged_at` が無い**」に変えた。

`llm_tags: []` は記事の生成時に全件へ書かれる既定値なので、
**「LLMが見て該当なしと判断した」と「一度も見ていない」がデータ上まったく区別できなかった**。
時刻の有無で切ることでこれが分かれる。

- **なぜ急いだか**: 無料枠が **15 RPM** と判明し、クォータが律速になったため。
  再判定はリクエスト予算を直接食う。実測では次回候補232件のうち **138件（59%）が却下済みの再投入**だった
- **②と③で同じ規則を保つ**。`tag-export` からも却下済みは出ない
  （人が見れば付けられる可能性はあるが、外すと毎回同じ却下済みの山を書き出すことになる）

#### taxonomy を増やしたときは再判定させる

フラグは恒久的なので、**`taxonomy/tags.yaml` にタグを足しても過去の却下済み記事には二度と適用されない**。
見直したいときは先にフラグを消す:

```bash
pnpm retag --llm-reset
```

`retag` のルールベース再付与に加えて `llm_tagged_at` を全件から削除し、次回の `collect` で再判定させる。
削除件数はログに出る。

**自動で無効化する方式は採らなかった**（taxonomy のハッシュを持たせて変わったら全消しにする案）。
15 RPM の制約下では**タグを1個足すたびに数千件の再判定が走り、数日かけて無料枠を食い潰す**ため、
明示的なコマンドにして「いつ再判定するか」を人が決める形にした。

### 残る対処案

- `taxonomy/tags.yaml` に受け皿のタグを足す — キュレーションの対象を広げる判断になるため保留中

design.md の B-2 完了条件「付与率95%以上」は、上記を入れないと到達できない見込み
（製品告知の除外後も付与率は58.8%でほぼ変わらなかった。削除した904件のタグ付与率が
コーパス全体とほぼ同じだったため）。**処理済みフラグは付与率を上げるものではない**——
再判定を止めて予算を新着に回すための変更で、付与率そのものは taxonomy 側の話。

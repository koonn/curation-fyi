# 和訳の運用

英語記事に**和訳見出し**（`title_ja`）と**3行サマリ**（`summary_ja`）を付ける。
生成は Issue #6 で作った Gemini 無料枠のバッチ呼び出しに乗っており、
タグ付けと同じ `LlmRunner` でリクエスト予算を共有する。

## 対象

`language === "en"` かつ `title_ja` を持たない記事から、**social（HN・はてブ）を除いたもの**。
新しい順に処理する。タグ付けと同じ規則で、分類は `@curation-fyi/shared` の `CATEGORIES` を使う。

日本語記事は原文で読めるので対象外（3行サマリも付けない）。

## 処理済みの判定

**`title_ja` の有無がそのまま処理済みフラグを兼ねる。** `llm_tagged_at` のような別フラグは無い。
タグ付けでフラグが必要だったのは「該当タグなし」が正当な結果で既定値の `[]` と区別できなかった
ためだが、和訳見出しは正当に空になることがないので同じ問題が起きない。

`summary_ja: []`（3行を作らなかった記事）が出ても、`title_ja` が入っていれば再処理されない。

## 実行

`collect` に組み込まれているので、通常は cron で新着分が処理される。
手動で回すときは GitHub Actions の **translate** ワークフロー（`workflow_dispatch`）を使う。

| 入力 | 意味 |
|---|---|
| `limit` | 処理する記事数の上限 |
| `source` | ソースを絞る（カンマ区切り。空なら全ソース） |
| `dry_run` | 保存せず結果をログに出すだけ（**既定 true**） |

```sh
gh workflow run translate.yml -f limit=25 -f dry_run=false
```

ローカルでも `pnpm translate --limit 10 --source acm-queue --dry-run` で同じことができるが、
`GEMINI_API_KEY` が要る。**キーを持たない環境ではワークフロー経由が正規の手順**。

`concurrency` は collect と同じグループにしてある。`data/articles` は月ファイルを全量
書き直す方式（`store.saveAll`）なので、collect と同時に走ると互いの書き込みを失う。

## タイトルしか無い記事には3行サマリを付けない

記事本文は取得しない。LLM に渡すのは**タイトルと、あれば RSS 由来の300字要約だけ**。
ACM Queue のようにフィードに `<description>` が無いソースはタイトルしか入力が無い。

プロンプトで「情報が足りなければ行を減らすか空配列にする」と明示してあり、
**実測でタイトルのみの記事4件すべてがサマリ空で返った**（2026-08-22）。
和訳見出しだけが付き、3行は捏造されない。特別なコード分岐は無く、プロンプトが担保している。

サマリの品質は**入力の抜粋の質で決まる**。`fetchers/rss.ts` の `SUMMARY_MAX = 300` で
打ち切られた抜粋が導入部で終わっている記事では、出力も「〜について議論する」という
meta 記述になりやすい。`SUMMARY_MAX` を上げれば改善する見込みだが、`summary` は
打ち切った状態で保存されるため既存記事に効かせるには再取得が要る。

## 表示

`packages/site/src/lib/load-articles.ts` の `displayTitle()` / `displaySummaryLines()` を通す。
和訳を持たない記事は従来どおりの表示になる。

反映先は4つ。**data/ を読む面を増やしたらここも確認すること**:

| 面 | 扱い |
|---|---|
| `ArticleCard.astro` | 和訳を `h2`、原題をその下に小さく。3行があれば `line-clamp-2` を外す |
| `a/[id].astro` | Pagefind の索引入力。**和訳を載せないと日本語で検索しても英語記事が引けない**。原題と原文要約も残すので英語からも引ける |
| `feed.xml.ts` | 和訳があれば見出しに使う |
| `recent.json.ts` + `FilterBar.tsx` | FilterBar はフィルタ適用時にクライアント側で自前のカードを描くので、和訳を入れないとフィルタした瞬間に英語見出しへ戻る。`summary_ja` は入れない（要約を描画しないため転送量が増えるだけ） |

`recent.json` の転送量は和訳1件あたり平均64バイト。全EN記事に入ると
**gzip 162KB → 218KB（+35%）** の見込み（2026-08-22 実測ベース）。

## デプロイの連鎖

translate は `data/` を書いて push するが、**`GITHUB_TOKEN` による push はワークフローを
起動しない**（再帰防止の仕様）ため、`deploy.yml` の `workflow_run` に `translate` を
入れてある。**`data/` を書くワークフローを増やしたら必ずここにも足すこと**——
足し忘れてもエラーにはならず「本番だけ古いまま」という形で出るので気づきにくい。

## 残っている制約

- **全件バックフィル（約1,500件＝61リクエスト）は 15 RPM に確実に当たる。**
  429 を受けて `retryDelay` 秒待って再開する処理を先に入れる必要がある
  （現状は上限に当たると打ち切って正常終了し、未処理分は次回に回る）
- 固有名詞の音訳を誤ることがある。実測: `Jim Highsmith` → 「ジム・ハイミスミス」
- プロンプトを変えて作り直したくなったときのリセット手段は、まだ作っていない
  （タグ付けの `retag --llm-reset` と同型のものが要る）
